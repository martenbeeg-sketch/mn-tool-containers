# BindCraft2 GPU Acceleration Evaluation Playbook

**Purpose:** determine how much of Anthropic's earlier BindCraft/ColabDesign acceleration is already present in current BindCraft2 (BC2), benchmark the remaining opportunities on RTX 4090 and RTX 5090, and only then decide whether code-level optimization is worth porting.

**Status reviewed:** 2026-10-07  
**Current BC2 repository reviewed:** `PacesaLab/BindCraft2` (current default branch; GitHub code-search snapshot resolved at commit `5bac63cd2d4e7ed3d5077ba4fc5966e0352038e4`)  
**Anthropic optimization repository reviewed:** `anthropics/uplifting-biomolecular-modeling`  
**Relevant Anthropic paper:** *Accelerating open-source biomolecular models with Claude* (Science et al., 2026)

---

## 1. Executive decision tree

Do **not** try to install the old Anthropic ColabDesign optimization kit directly into BindCraft2 first.

The old kit was built against:

- old BindCraft commit `efb5bfeb...`
- ColabDesign 1.1.3 at `e31a56fe...`
- JAX/JAXLIB 0.6.0
- the old architecture where BindCraft called ColabDesign's AF2 design machinery

Current BC2 is materially different:

- the AF2/ColabDesign-derived design engine is vendored and modified inside BC2;
- BC2 currently requires JAX `>=0.11,<0.12`;
- BC2 already implements persistent compiled-graph caching;
- BC2 buckets sequence lengths and can compile the next length in parallel;
- BC2 dynamically decides whether AF2 subbatching is needed;
- BC2 has a fused `cuDNN` attention path;
- BC2 has optional `cuEquivariance` triangle multiplication;
- BC2 can pack multiple trajectory workers on a GPU.

Therefore:

> **First benchmark BC2's native fast paths. Then profile. Only port missing Anthropic kernels if profiling shows they remain bottlenecks.**

Recommended order:

1. Verify which fast paths are actually active on the 4090 and 5090.
2. Benchmark `stock attention → auto/cuDNN → auto/cuDNN + cuEquivariance`.
3. Test unchunked execution (`subbatch_size=null`) where memory permits.
4. Compare 4090 vs 5090 at identical settings and total padded residue counts.
5. Run a small quality-equivalence experiment.
6. Profile the fastest stable BC2 configuration.
7. Only then consider porting missing FlashPairformer/Anthropic optimizations.

---

# 2. What Anthropic optimized in the old BindCraft/ColabDesign stack

Anthropic's ColabDesign kit accelerated the **binder hallucination stage**, i.e. the repeated differentiable AlphaFold-Multimer forward/backward passes used to optimize a binder sequence. It did **not** accelerate all later BindCraft stages.

Their H100 benchmark reported a geometric-mean **~4.9× speed-up per design step in Fast mode** for the old ColabDesign/BindCraft implementation. This number must **not** be assumed for BC2 because BC2 has already changed several of the bottlenecks that produced that gain.

## 2.1 Exact-mode optimizations in the old kit

These were designed to preserve identical outputs:

### `compilecache`
Persistent JAX/XLA compilation cache so later processes do not compile the same program again.

### `lowercache`
Anthropic went beyond ordinary JAX compilation caching: it serialized/later loaded the already lowered/compiled design executables. This avoided repeatedly tracing and lowering the Haiku/ColabDesign design programs before JAX could even consult its compilation cache.

### `parcompile`
Parallelized LLVM/XLA compilation over available CPU cores.

### `hoist_prev`
Kept AlphaFold recycle-state arrays on the GPU instead of creating/moving the same recycle structures through the host path.

---

## 2.2 Fast-mode optimizations in the old kit

These allowed small numerical re-associations but were checked against the variation of the original workflow.

### `nosub` / `nosub_fn`
Old ColabDesign automatically subbatched the AF2 design calculation above **384 tokens**. Anthropic removed that chunking when the fused kernels made the full computation fit in memory.

This was reported as the **largest contributor at longer input sizes**.

### `triatt`
Custom FlashPairformer-style triangle/AF2 attention kernels:

- pair bias and masks read inside the kernel;
- online softmax;
- large attention matrices not materialized in GPU memory;
- fused backward path.

### `trimul`
Fused triangle multiplication:

- input normalization;
- projections;
- gating;
- triangle product;
- output normalization/projection;
- custom backward.

### `transition`
Fused AF2 Transition block:

`LayerNorm → Linear(C→4C) → ReLU → Linear(4C→C)`

The large `4C` intermediate was kept on-chip rather than written to global memory.

### `proj`
Combined Q/K/V/gating projections into fewer matrix multiplications and correspondingly fused gradient operations.

### `opm_fold`
Algebraically rearranged AF2 OuterProductMean to avoid the expensive large intermediate generated by the stock operation.

### `ln`
Fused LayerNorm kernels.

### `txla`
A forward-only custom-call path for triangle attention using preselected GPU kernels.

# 3. What current BindCraft2 already implements

The table below is the key comparison.

| Old Anthropic optimization | Current BC2 status | Action |
|---|---|---|
| Persistent XLA compile cache | **Implemented** | Test that it is persistent on each GPU |
| Reuse compiled shapes | **Implemented** with length bucketing | Keep enabled |
| Compile next shape while current trajectory runs | **Implemented** (`compile_next_length`) | Keep enabled |
| Hard >384-token subbatch removal | **Old limitation is superseded** by BC2 dynamic `subbatch_size` | Benchmark `auto` vs `null` |
| Fused attention | **Implemented differently** using JAX `dot_product_attention`, automatically probing cuDNN | Benchmark first |
| Fused triangle multiplication | **Available** through `cuEquivariance` | Important: off by default; benchmark |
| GPU-aware worker packing | **Implemented in BC2** | Benchmark separately from single-worker latency |
| GPU-memory-aware subbatch choice | **Implemented** | Verify on 4090 vs 5090 |
| Length bucketing | **Implemented** (`length_bucket_size`, default 32) | Useful for compile reuse |
| Dedicated Anthropic FlashPairformer triangle-attention kernels | **No equivalent identified in current BC2 source** | Candidate only after profiling |
| Anthropic fused Transition kernel | **No equivalent identified** | High-priority candidate after profiling |
| Anthropic fused Q/K/V/gating projections | **No equivalent identified** | Candidate after profiling |
| Anthropic `opm_fold` OuterProductMean rewrite | **No equivalent identified** | Candidate after profiling |
| Anthropic serialized lowered executables (`lowercache`) | **No equivalent identified** | Only useful if trace/lowering remains material |
| Anthropic Pallas kernel suite | **No Pallas-specific equivalent identified** | Do not port blindly |

Current BC2 has its own acceleration module at:

`bindcraft/af/accel.py`

Important current paths include:

- `supported_attention_backend("auto")`
- fused JAX/cuDNN `dot_product_attention`
- `cuequivariance_jax.triangle_multiplicative_update`
- fallback to stock/chunked paths when fused attention cannot be used

BC2's default settings currently include:

```json
{
  "attention_backend": "auto",
  "use_cueq": false,
  "subbatch_size": "auto",
  "length_bucket_size": 32,
  "compile_next_length": true
}
```

So the **first untested optimization to try is `use_cueq=true`**, not an Anthropic code port.

# 4. Benchmark philosophy

Separate four questions that are often accidentally mixed together.

## A. Cold-start latency

How long does a brand-new shape/GPU configuration take when nothing is compiled?

This measures:

- JAX tracing;
- XLA lowering/compilation;
- model initialization;
- first-run overhead.

## B. Warm single-trajectory speed

How long does one trajectory take after the required programs are compiled?

This is the closest BC2 analogue to Anthropic's "seconds per design step" comparison.

## C. Campaign throughput

How many trajectories per hour can the card produce when BC2 is allowed to pack workers?

This matters more for production use than single-trajectory latency.

## D. Design quality

Does an acceleration mode measurably change:

- trajectory survival;
- final confidence metrics;
- interface metrics;
- candidate yield;
- accepted-design yield?

A mode that is 20% faster but systematically lowers design quality is not an improvement.

Before running a campaign:

```bash
python - <<'PY'
from bindcraft.af import accel

print("auto attention:", accel.supported_attention_backend("auto"))
print("cuEquivariance available:", accel.cuequivariance_available())
PY
```

Desired output on NVIDIA:

```text
auto attention: cudnn
cuEquivariance available: True
```

Interpretation:

- `cudnn` means the current BC2 fused attention path is available.
- `stock` means `attention_backend=auto` is silently selecting the unfused BC2 path.
- `False` for cuEquivariance means `use_cueq=true` cannot yet test the fused triangle-multiplication path; fix installation before drawing performance conclusions.

Record this separately for **4090 and 5090**.

# 7. Choose benchmark cases

Use the same target, binder format, losses, stages and seeds between modes.

Run at least two size regimes:

### Case S — normal/small

A representative routine design where total **padded target + binder length is ~200–300 residues**.

The shipped PD-L1 example is suitable for an initial smoke benchmark.

### Case L — long

A case with total **padded target + binder length ≥400–500 residues**.

This is essential because:

- memory scales strongly with pair representations;
- the old ColabDesign optimization gained most above its 384-token subbatch threshold;
- differences between 24-GB 4090 and 32-GB 5090 are more likely to appear here.

If your production projects never approach this range, Case S is more important and the old 4.9× Anthropic figure is even less transferable.

---

# 8. Make the benchmark deterministic

Use BC2's benchmark core profile:

```json
"core": "benchmark"
```

BC2 documents this profile as fixing the campaign seed and disabling autotuning/desperation, which is exactly what is wanted for A/B benchmarking.

For the **compute benchmark**, also use:

```json
{
  "trajectory_only": true,
  "max_trajectories": 8,
  "workers_per_gpu": 1,
  "auto_multi_gpu": false,
  "sparse_output": true
}
```

Why:

- `trajectory_only` isolates the gradient-design/hallucination stage.
- one worker removes throughput/packing effects.
- `sparse_output` reduces unrelated I/O.
- 8 trajectories gives one compile/cold trajectory plus several warm observations.

Use a **fixed binder length**, not a range, for the first comparison. This ensures every trajectory uses the same padded shape and makes compilation behavior easier to interpret.

# 11. Cold vs warm compilation tests

BC2 already has a persistent per-card XLA cache. Test it explicitly rather than mixing compilation into the main timing.

## Cold test

Use an isolated cache:

```bash
export JAX_COMPILATION_CACHE_DIR="$PWD/bench_cache/5090_A2_cold"
```

Run the arm once.

## Warm test

Use the **same cache** but a new project folder:

```bash
export JAX_COMPILATION_CACHE_DIR="$PWD/bench_cache/5090_A2_cold"
```

Run the same shape/settings again.

The second run should benefit from the compiled graph cache.

Do this for one representative arm rather than every arm unless compilation latency is itself important.

# 12. Read BC2's own timing data

Current BC2 records timing in the `Timing` column of its stage tables, including:

- whether a trajectory required a fresh compilation;
- design time;
- worker;
- reprediction time when applicable.

BC2 also exposes a helper that summarizes campaign timing.

```bash
python - <<'PY'
from bindcraft.campaign_output import campaign_timing
import json

folder = "PATH_TO_CAMPAIGN"
print(json.dumps(campaign_timing(folder), indent=2))
PY
```

For Phase 1 use:

- median warm `design_seconds`;
- mean warm `design_seconds`;
- trajectories/hour;
- cold first-trajectory time;
- peak GPU memory;
- GPU utilization.

Do **not** compare only complete command wall time: compilation and I/O can hide the effect on the gradient-design loop.

# 13. Monitor GPU utilization and memory

In a second terminal:

```bash
nvidia-smi \
  --query-gpu=timestamp,name,utilization.gpu,memory.used,power.draw,clocks.sm \
  --format=csv \
  -l 1 > gpu_monitor.csv
```

For each arm record:

- peak memory;
- median GPU utilization during warm trajectories;
- obvious periods where the GPU is idle;
- power draw;
- whether 4090 or 5090 is memory-limited.

If utilization repeatedly drops while the CPU is active, optimization should target host/JAX scheduling rather than another GPU math kernel.

# 14. Phase 1 go/no-go criteria

For each GPU calculate speed-up relative to A0:

```text
speed-up = median(A0 warm design_seconds) /
           median(test warm design_seconds)
```

Suggested interpretation:

| Result | Interpretation |
|---|---|
| A1 >> A0 | BC2's cuDNN attention already matters strongly |
| A1 ≈ A0 | attention is not the dominant bottleneck for this size |
| A2 >> A1 | cuEquivariance triangle multiplication is worth enabling |
| A2 ≈ A1 | triangle multiplication is not dominant, or the fused path is not serving important calls |
| A3 >> A2 | automatic subbatching is conservative for this GPU/shape |
| A3 ≈ A2 | `auto` is already choosing unchunked execution or chunking is not costly |
| A3 OOM on 4090 but not 5090 | expected useful differentiation from the 5090's larger VRAM |
| GPU utilization remains low | profile host/tracing/scheduling before writing kernels |

Do not port any Anthropic kernel yet.

# 15. Phase 2 — quality-equivalence experiment

The fastest mode must be checked for design behavior.

Use:

- the same target;
- same fixed binder length;
- same `core=benchmark`;
- same campaign seed;
- at least **30 trajectories per arm**;
- A0 versus the best native mode from Phase 1.

For this stage keep `trajectory_only=true` initially.

Compare distributions, not one trajectory.

Record:

- fraction completing each design stage;
- termination reasons;
- final trajectory pLDDT;
- i_pTM;
- i_pAE;
- interface/contact metrics used by your campaign;
- final loss terms;
- structural pathologies/clashes.

Because fused kernels can change floating-point reduction order, exact sequence identity is **not** the correct requirement. The appropriate question is whether the accelerated mode causes a systematic quality shift.

Suggested acceptance criterion:

> Keep the accelerated mode if speed improves reproducibly and no major design-quality metric shows a consistent adverse shift larger than ordinary seed-to-seed variability.

If A2/A3 materially changes quality, repeat with more trajectories before deciding.

---

# 16. Phase 3 — end-to-end production check

Once a native fast mode passes Phase 2, run the normal BC2 pipeline including:

- ProteinMPNN;
- held-out AF validation;
- final filters/ranking.

Use the same number of attempted trajectories rather than "run until N accepted", otherwise one arm may simply run much longer.

Compare:

- candidates per 100 trajectories;
- accepted designs per 100 trajectories;
- accepted i_pDAE / i_pTM / i_pAE distributions;
- wall-clock trajectories/hour;
- accepted designs/GPU-day.

**Accepted designs/GPU-day** is the most useful production metric.

---

# 17. Phase 4 — test BC2 worker packing separately

Only after single-worker latency is understood.

Current BC2 automatically packs workers based on free GPU and host memory.

Test:

```json
"workers_per_gpu": 1
```

then:

```json
"workers_per_gpu": 2
```

then allow:

```json
"workers_per_gpu": "auto"
```

Use a fixed number of total trajectories.

Measure:

```text
campaign throughput = total trajectories / wall-clock hours
```

The fastest single trajectory is not necessarily the highest-throughput configuration.

Expected:

- 4090 may reach its memory limit earlier;
- 5090 may profit from either unchunked execution or more simultaneous workers;
- the best settings for latency and throughput can differ.

---

# 18. Only now profile the remaining bottlenecks

Profile the **fastest quality-safe BC2 configuration**, not A0.

Useful tools:

```bash
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none \
  -o bc2_profile \
  bindcraft design YOUR_BENCHMARK.json
```

Focus on a warm trajectory after compilation.

Look for time in:

1. attention;
2. triangle multiplication;
3. Transition MLP;
4. OuterProductMean;
5. Q/K/V/gating projections;
6. JAX launch/synchronization overhead;
7. host↔device copies;
8. CPU-side work or output;
9. tracing/lowering between trajectories.

Only optimize a component if it occupies a meaningful fraction of warm runtime.

A 2× speed-up of a kernel consuming 5% of runtime gives only ~2.6% end-to-end improvement.

# 19. Candidate code optimizations, in priority order

The exact order should be updated after profiling.

## Candidate 1 — fused Transition block

**Why interesting:** current BC2 still appears to use the conventional AF2 Transition implementation, while Anthropic had a dedicated fused kernel.

Potential implementation:

`LayerNorm + Linear(C→4C) + activation + Linear(4C→C)`

with the `4C` intermediate kept on chip where possible.

### Test requirement

- unit-test forward values;
- unit-test gradients;
- deterministic repeated-run test;
- 30+ trajectory quality comparison;
- benchmark by padded residue size.

**Priority:** high if Transition is >10–15% of warm GPU time.

---

## Candidate 2 — projection fusion around attention

Anthropic fused Q/K/V/gating input projections into fewer GEMMs.

Current BC2's fused attention primarily optimizes the attention calculation itself; an equivalent projection fusion was not identified in the reviewed code.

**Priority:** high if profiler shows many small projection GEMMs/kernel launches.

---

## Candidate 3 — specialized FlashPairformer triangle attention

Do not assume it will beat current `jax.nn.dot_product_attention(... implementation="cudnn")`.

Benchmark a prototype against the **current cuDNN path**, not against stock attention.

Required comparison:

```text
BC2 stock attention
BC2 cuDNN attention
prototype FlashPairformer attention
```

If cuDNN is already close, maintaining a custom kernel may not be justified.

**Priority:** medium/high only if cuDNN attention remains a major bottleneck.

---

## Candidate 4 — OuterProductMean algebraic rewrite

Anthropic's `opm_fold` avoided a large intermediate by changing contraction order.

No corresponding BC2-specific optimization was identified in the current source.

**Priority:** profile-dependent.

---

## Candidate 5 — executable `lowercache`

Anthropic serialized already lowered/compiled executables, whereas BC2 currently has persistent XLA compilation caching and length reuse.

This is worthwhile only if profiling/timing shows a significant repeated cost between trajectories despite a warm XLA cache.

Measure:

```text
new process, warm XLA cache
same process, next trajectory
```

If the difference is small, do not implement this.

**Priority:** low unless short trajectories spend appreciable time tracing/lowering.

---

## Candidate 6 — make cuEquivariance automatic

If Phase 1/2 shows that:

- `use_cueq=true` works on both 4090 and 5090;
- it reliably accelerates;
- quality does not shift;

then the simplest useful code contribution may be an **auto** mode rather than another custom kernel.

For example conceptually:

```text
use_cueq = auto
    -> probe availability
    -> run supported fused triangle multiplication
    -> fallback safely
```

This is lower-maintenance than porting a private Pallas kernel stack.

---

# 20. What NOT to do first

Do not:

- transplant Anthropic's whole `colabdesign` kit into BC2;
- downgrade BC2 to JAX 0.6 just to run that kit;
- quote the old ~4.9× H100 speed-up as an expected BC2 result;
- optimize compilation before measuring warm trajectory time;
- optimize only on H100 assumptions;
- compare different binder lengths between GPU/mode arms;
- benchmark with autotuning/desperation enabled;
- judge numerical equivalence from one seed;
- optimize a kernel before profiling the current cuDNN/cuEquivariance configuration.

# 24. Decision gates

Proceed to a code port only when all of these are true:

- native BC2 fast paths have been benchmarked;
- current cuDNN attention has been compared against stock;
- `use_cueq=true` has been tested;
- subbatch behavior is understood;
- warm timing is separated from compilation;
- quality equivalence has been checked;
- profiler identifies a remaining hot operation;
- expected end-to-end gain justifies maintenance burden.

A reasonable threshold for custom-kernel work is:

> **Target ≥15–20% expected reduction in warm trajectory time**, not merely a large microbenchmark speed-up of a minor kernel.

# Bottom line

The old Anthropic result is highly relevant because it demonstrates that the AF2/ColabDesign hallucination engine contains substantial systems-level optimization opportunities.

But **BindCraft2 is no longer the old BindCraft/ColabDesign stack**.

BC2 has already adopted several of the same principles:

- persistent compilation caching;
- shape reuse;
- asynchronous next-shape compilation;
- dynamic subbatching;
- fused cuDNN attention;
- optional cuEquivariance triangle multiplication;
- GPU-aware campaign parallelism.

Therefore the correct project is **not "apply the Anthropic patch to BC2."**

It is:

> **Benchmark the native BC2 fast paths on 4090/5090 → identify the remaining bottleneck → selectively port only the missing optimization that matters.**

The first practical test should be **`attention_backend=auto` + `use_cueq=true`**, followed by **`subbatch_size=null` on the 5090 if it fits**.
